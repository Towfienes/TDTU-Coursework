SECTION 6 — LIKELY QUESTIONS & SHORT ANSWERS
------------------------------------------------------------

Q1: Does modern Android trust user-installed Certificate Authorities by default?
A1: No. Since Android 7.0 (API level 24), Android applications targeting modern API levels trust only system-installed root CAs by default. User-installed CAs are ignored unless the application explicitly opts in using a custom Network Security Configuration file in debug mode.

Q2: What is the fundamental difference between standard HTTPS/TLS and Certificate Pinning?
A2: Standard HTTPS validates the server's certificate against ANY trusted Certificate Authority in the device's trust store. Certificate Pinning adds an application-specific trust restriction on top of normal TLS, requiring the server's certificate or public-key SHA-256 hash to match a specific expected identity, bypassing rogue or compromised CAs.

Q3: Why is pinning the public key (SHA-256) preferred over pinning the entire leaf certificate?
A3: Leaf certificates expire frequently (often annually or every 90 days), which would force app updates whenever a certificate renews. Pinning the public key SubjectPublicKeyInfo (SPKI) hash allows the server certificate to be renewed using the same key pair without breaking mobile client connectivity.

Q4: What happens if a server certificate expires or rotates and the app doesn't have a backup pin?
A4: If the public key changes and no matching backup pin was configured in the app, all mobile clients will reject the TLS connection (SSLPeerUnverifiedException), causing a complete application-wide denial of service until an updated app build is published and installed. This is why production pinning requires backup pins and key rotation strategies.

Q5: Does Certificate Pinning permanently prevent all Man-in-the-Middle attacks on rooted test devices?
A5: In a production environment on normal consumer devices, yes, it effectively prevents proxy interception. However, on a rooted test device under the tester's control, pinning can be bypassed using runtime instrumentation tools like Frida, Objection, or Xposed by hooking the certificate verification methods in memory.

Q6: Why is Jetpack EncryptedSharedPreferences not recommended as the modern solution on Slide 9?
A6: EncryptedSharedPreferences has been deprecated in recent AndroidX Security releases due to underlying bugs and performance overhead. Modern Android security emphasizes using the hardware-backed Android Keystore directly to protect cryptographic keys and applying application-level encryption for sensitive assets.

Q7: What is the purpose of android:dataExtractionRules introduced in Android 12?
A7: Historically, android:allowBackup="false" was an all-or-nothing flag. Android 12 introduced dataExtractionRules, an XML configuration allowing developers to define granular policies specifying exactly which directories or files are excluded from cloud backups and device-to-device migration transfers.
