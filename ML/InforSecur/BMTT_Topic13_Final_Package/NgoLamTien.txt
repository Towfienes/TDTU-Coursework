SLIDE 3 — Android Security Foundation (Kernel-Level Sandboxing & Components)
- Target time: 1 minute 15 seconds
- Purpose: Explain how Android enforces process isolation and component boundaries.
- Must explain:
  1. Linux Application Sandbox: Each app gets a unique, immutable Linux UID (e.g., u0_a142) at install time, running in an isolated process with an independent Android Runtime (ART) instance.
  2. Kernel File Permissions: App directories (/data/data/<package>) have strict 0700 DAC permissions, preventing ordinary apps from accessing each other's memory or files.
  3. The 4 Core Components: Activity (visual UI), Service (background work), BroadcastReceiver (async event listener), and ContentProvider (structured data interface for IPC).
  4. AndroidManifest.xml: Authoritative declarative contract parsed at install time.
- Main takeaway: Android adapts the multi-tenant Linux OS security model to treat each mobile application as an isolated user with strict process and file boundaries.
- Do not say: Do not say that Android sandboxing makes applications 100% immune to all vulnerabilities; sandboxing isolates processes, but application-level logic flaws can still be exploited.

SLIDE 4 — Permission Model & AndroidManifest.xml (Access Control & Governance)
- Target time: 1 minute 30 seconds
- Purpose: Detail permission protection levels and the security implications of component exposure.
- Must explain:
  1. Four Permission Levels:
     - Normal (install-time, low risk, auto-granted, e.g., INTERNET).
     - Dangerous (runtime user consent required, high risk, e.g., CAMERA, LOCATION).
     - Signature (vendor protection, auto-granted only if signed with the exact same developer certificate).
     - Special / Privileged (system-level capabilities, manual user activation in system settings).
  2. The android:exported Gateway:
     - android:exported="false": Component is strictly internal; cannot be reached through normal external launching.
     - android:exported="true": Component can be reached by other apps, subject to permissions or access controls.
  3. Android 12+ mandate: Explicit declaration of android:exported is mandatory for components with intent filters.
  4. Core Nuance: "Exported does not automatically mean vulnerable." A vulnerability occurs only when an exposed endpoint lacks sufficient authorization, permissions, caller checks, or input validation.
  5. Principle of Least Privilege: Expose only what is strictly required and gate exposed components.
- Main takeaway: Declaring android:exported="true" opens an external communication gateway, but vulnerability depends on whether the component properly enforces authorization, permissions, and input validation.
- Do not say: DO NOT SAY that exported="true" means ANY app can launch it unconditionally without restrictions, and DO NOT SAY that an exported component is automatically vulnerable.

[SLIDE 2 — WHY ANDROID SECURITY MATTERS (~1 minute 00 seconds)]
"When developers think about mobile security, a common mistake is treating Android as a single perimeter. In reality, a modern client-server application spans multiple distinct operational layers.

If you look at the top flow on this slide, an end user interacts with the Android client, which executes local business logic, reads and writes local storage, dispatches inter-process messages, and communicates with cloud APIs over HTTPS.

Because data and execution flow across these layers, Android establishes four essential security boundaries:
First, the Permissions Boundary, which gates access to sensitive device hardware like the camera and location.
Second, the IPC and Intent Boundary, which governs message passing between separate application processes.
Third, the Storage-at-Rest Boundary, which isolates private databases and files using Linux user IDs.
And fourth, the Network Transit Boundary, which protects client-server communication across untrusted networks.

Our core takeaway here is simple: Android security requires defense-in-depth across all four boundaries. If any single boundary is misconfigured, the security of the entire application can collapse."


[SLIDE 3 — ANDROID SECURITY FOUNDATION (~1 minute 15 seconds)]
"Now, let us examine how Android implements this security foundation at the operating system level.

Android departs from traditional desktop computing by adapting the multi-tenant Linux OS model. Upon installation, the system assigns each application a unique, immutable Linux User ID—such as u0_a142. Every app executes inside its own dedicated Linux process running an independent instance of the Android Runtime virtual machine. Furthermore, the operating system applies strict discretionary access control permissions—mode 0700—to the application's private directory under /data/data/<package_name>. This ensures that an ordinary third-party app cannot read another app's memory or inspect its private files.

Within this sandbox, applications are built from four core modular components:
Activities, which render visual interactive screens;
Services, which handle long-running background tasks without a user interface;
BroadcastReceivers, which listen asynchronously for system-wide or internal event signals;
And ContentProviders, which provide structured data access and abstract SQLite databases for inter-process communication.

All of these components and their security policies are declared in a single authoritative blueprint: the AndroidManifest.xml file. Parsed at install time, the manifest defines the application's attack surface through component exposure and permission declarations."


[SLIDE 4 — PERMISSION MODEL & ANDROIDMANIFEST.XML (~1 minute 30 seconds)]
"Because apps often need device resources beyond their isolated sandbox, Android provides a granular Permission Model categorized into four protection levels.

On the left, you can see these four tiers:
Normal permissions cover low-risk operations like accessing the network state and are automatically granted at install time.
Dangerous permissions govern sensitive private data—such as camera, contacts, and fine location—and require explicit runtime prompts where the user must give informed consent.
Signature permissions represent vendor-level trust: Android grants them automatically only if the requesting app is signed with the exact same cryptographic certificate as the declaring app.
And Special permissions regulate advanced capabilities like system alert windows, requiring users to manually toggle settings.

Now look at the right side of the slide, where the manifest controls component reachability through the android:exported attribute.
When android:exported is 'false', the component is private and cannot be launched by normal external component launching.
When android:exported is 'true', external applications may reach the component. 

Here is a critical nuance: exported does not automatically mean vulnerable. An exported component is only vulnerable if it exposes sensitive functionality without verifying caller permissions, enforcing authorization, or validating incoming input. Furthermore, since Android 12, developers must explicitly declare android:exported for any component with intent filters.

This brings us to the Principle of Least Privilege: keep internal components non-exported by default, and strictly protect any necessary public interfaces."

SECTION 6 — LIKELY QUESTIONS & SHORT ANSWERS
------------------------------------------------------------

Q1: Why does Android assign a unique Linux UID to every application instead of running all apps under the current mobile user?
A1: Traditional desktop systems run all user apps under a single user ID, allowing any app to access all user files. Android treats every app as an independent, isolated user in a multi-tenant Linux model. This ensures strict OS-level memory and file isolation via kernel Discretionary Access Control.

Q2: Does setting android:exported="true" automatically make an Activity vulnerable?
A2: No. Exported simply means the component is externally reachable. It is only vulnerable if it performs sensitive actions without verifying caller identity, enforcing permission checks, or validating incoming Intent parameters.

Q3: What changed regarding android:exported in Android 12?
A3: In Android 11 and earlier, declaring an <intent-filter> caused android:exported to default to 'true' implicitly, which often led to accidental exposure. Android 12 (API level 31) made it mandatory to explicitly declare android:exported="true" or "false" whenever an intent filter is defined.

Q4: What is the security advantage of Signature permissions over Dangerous runtime permissions?
A4: Dangerous permissions rely on end-user prompts, which users may click through without understanding. Signature permissions are enforced cryptographically by the OS: only apps signed with the developer's private signing key can obtain the permission, enabling seamless and secure communication between a vendor's own suite of applications.

Q5: Can an unexported component (android:exported="false") ever be reached by another application?
A5: Under normal direct invocation, no. However, if the victim application has an exported proxy component that blindly forwards external Intents internally, an attacker can indirectly reach the unexported component via a Confused Deputy attack, which Thành will explain next.

Q6: What is the difference between Normal and Dangerous permissions from a user perspective?
A6: Normal permissions pose minimal risk and are granted silently at installation without prompting the user. Dangerous permissions access private user data or sensitive hardware and require an interactive system prompt at runtime where the user can allow or deny access.

SECTION 7 — IMPORTANT THINGS NOT TO SAY
------------------------------------------------------------

1. DO NOT SAY: "android:exported='true' means any app can launch it unconditionally."
   CORRECT PHRASING: "android:exported='true' allows the component to be reached by other apps, subject to permissions or access-control requirements."

2. DO NOT SAY: "Exported components are automatically vulnerable."
   CORRECT PHRASING: "Exported does not automatically mean vulnerable. A vulnerability exists when externally reachable functionality lacks authorization, permissions, or input validation."

3. DO NOT SAY: "Linux sandboxing stops all attacks on mobile devices."
   CORRECT PHRASING: "Sandboxing enforces OS-level process and file access control, but it cannot prevent application-level logic flaws or improper component exposure."

4. DO NOT SAY: "Dangerous permissions are granted when the user installs the app from Google Play."
   CORRECT PHRASING: "Since Android 6.0, dangerous permissions must be requested at runtime when the app actually needs the capability."
